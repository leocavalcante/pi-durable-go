## Implemented foundation

- Serialized commits across transcripts, submissions, tasks, and JSON documents (singletons and keyed families: `DocumentDefinition.Family`, `Tx.FamilyDocument`, `PutFamilyDocument`, `ReadFamilyDocument`, `RetireDocument`), and rewindable documents read as of an entry (`ReadDocumentAsOf`, `ReadFamilyDocumentAsOf`, upstream `snapshotAsOf`). Inside a commit, `Tx.ScanConversations`, `Tx.ScanTasks`, and `Tx.ScanEntries` page through records with upstream's filters and orders, `Tx.SubmissionByRequest` and `Tx.LatestEntryID` read single records, and `Tx.Fork` forks a conversation (upstream `scanConversations`, `scanTasks`, `scanEntries`, `submissionByRequest`, `latestEntryId`, `forkConversation`); detached snapshots, and watches that see stored commits and deferred progress once it is adopted. Transactions copy on write and commits store only what changed (`DeltaStorage`): SQLite keeps one row per record, JSONL appends change lines after a whole-State line and compacts under the same lock once they outweigh it, and memory storage applies changes to its copy.
- Uncertain storage failures poison the Session; caller writes rejected as unapplied roll back, while scheduler bookkeeping failures fail closed. Fatal failures end observers and waits, signal invocations, and close storage after admitted work drains. `Err`, `Done`, and `WaitClosed` expose admission/failure and shutdown completion.
- ID-based conversations, root creation, complete-Agent reconfiguration, transcript forks, and per-conversation provider session IDs.
- Input, write, and continue submissions follow upstream admission (spec §6): custom non-`pi.*` input-entry kinds/data, per-conversation request-ID deduplication, `WhenBusy` (`followUp`, `steer`, `reject`) and `WhenIdle: "reject"` (`ErrIdle`), `queued`/`placed`/`done`/`unanswered` statuses with the placed `Entry`, waiting, and queued-input withdrawal. Display-only writes settle immediately during a run unless a reset is queued. Queued items are placed at upstream's final and post-tools boundaries under `Settings.SteeringMode`/`FollowUpMode`, and the `pi.inbox` document (`Conversation.Inbox`) mirrors them in every commit.
- Run control lives in `pi.live` (upstream `LiveState`): `run`, `generation` attempt and retry note, tool slots, `compactions`, `compactionFailure`, and `runFailure` with upstream's reason codes. A generation runs one turn and hands the run to the next; `Settings.AfterFailedRun`, continue submissions, tool handoffs that continue in a new context, and `Agent.MaxTurns` (`turn_limit`) follow upstream ([plan 0004](docs/plans/0004-run-control-and-run-failures.md)).
- Generation and tool tasks persist intent and replay-safety policies. Custom tasks support checkpoints, timers, waiting, ownership, cancellation, restart abandonment, and background work; `OwnedTasks` and invocation-bound `AbortOwned` expose direct task children.
- Versioned documents support conversation/session/task scope; conversation history/forks include `latest`/`rewindable` and `initial`/`current`/`asOf` policies.
- Extensions provide ordered selections, same-name replacement, tool and section wrappers (`WrapTools`, `WrapSections`, applied in extension order; a wrap that renames or panics drops its target, and generation reports the panic as `extension_error`), hooks, and sections. Custom tasks get hooks too: `Extension.TaskHooks` registers handlers by task kind (upstream `hook(task, handlers)`), and the task runs them in extension order with `EachTaskHook`, which reports a failing handler as `extension_error` and goes on. Conversation/document watchers deliver bounded latest snapshots, not audit logs.
- Resets and explicit durable compaction are implemented. Task start/end times and per-attempt model/tool response durations are recorded.
- Local coding tools, a pure-Go OpenAI-compatible streaming adapter, and an optional installed Pi SDK adapter are available. Assistant-native replay data persists across tool rounds/restarts and is excluded from compaction summary input.
- The SDK bridge is separately based on `@earendil-works/pi-coding-agent` 1.5.2 and Node.js 22.19+; it is not the Durable runtime reference. See [model/README.md](model/README.md).

## Task outcomes and definition lifecycle

### Outcomes, invocation, and cleanup

Task-written outcomes are `completed`, `failed`, and `aborted`. A newly committed `failed` outcome requires a non-empty `Error`; optional `ErrorDetail` must be JSON. `completed` rejects error/detail/reason fields, and `aborted` may carry a `Reason`, not an `Error`. `faulted` carries an error and `orphaned` requires its blocked `Reason`; both are scheduler-only statuses: a handler error/panic or lack of checkpoint progress faults a task, while a blocked task explicitly aborted without a usable definition is orphaned. The scheduler bounds its generated persisted diagnostics to 4 KiB of valid UTF-8. Panic stacks are attached to volatile reports, never stored. Existing outcome records are not retroactively validated.

If a handler returns while its task is still `running`, a structurally changed checkpoint lets the next phase continue in the same invocation; returning without that progress faults it. A committed `pending`, `waiting`, or terminal transition ends that phase without the progress check. JSON object key order and numerically equivalent number spellings do not count as progress differences. The task-committed `pending` transition is a Go-specific yield; `waiting` waits on task IDs. Every outcome hold in `completing` drops memos immediately while retaining the checkpoint until finalization. Runtime gates are invocation-scoped, as in upstream v1.5.2's `#run`/`#runtime`/`#gated`: a continuing step does not revoke the runtime. Join phase-owned goroutines before returning when their writes must precede that phase's progress decision.

For built-in tasks, scheduler faults/orphans clean up in the terminal commit. Generation cleanup salvages a partial assistant message and ends the run (`faulted` with the message, or `orphaned` with its reason), recording `runFailure` and leaving queued submissions alone. Tool cleanup marks the slot done without a result entry; derived model context synthesizes a missing-result error message with upstream's details (`Message.Details`, `{"reason":"missing_result"}`). Compaction cleanup records `compactionFailure`, except for a cut-off abort handler.

### Resolution, migration, and inspection

A missing or incompatible definition alone does not terminalize a task. Inspection derives `missing_task`, `task_too_old`, or `migration_failed`; blocked tasks remain live until a fitting definition is installed or an abort settles them as orphaned. `TaskDefinition.Migrate` now takes `(fromVersion, input, checkpoint)` and returns migrated input and checkpoint. It runs on the serialized Session line during reservation and may also run as an abort/orphan eligibility probe; successful migrated values and `running` are committed atomically at reservation, while a successful probe is not persisted and may be evaluated again. Migration must be pure, deterministic, bounded, and must not call Session/registry APIs or perform external effects. During ordinary reservation, a failed migration leaves the task record unchanged; an explicit abort can instead settle it as `orphaned` with `migration_failed`. Failures are cached/reported once per task and effective definition identity for the open Harness; reinstalling a definition changes identity, and reopening starts a fresh cache and permits retry.

Each successful extension install gives its task definitions a new Go identity. Reinstalling the same unchanged extension creates a new identity and can trigger migration retry or handover; unrelated installs preserve existing identities. This install-based approximation differs from upstream object identity. The Harness resolves built-ins `pi.generation`, `pi.tool`, and `pi.compaction` before extension tasks. `CompactionExtension()` is deprecated; legacy registration is accepted but cannot override the built-in and is unnecessary.

`Harness.Inspect(ctx)` is read-only: it captures task records, scheduling/cache state, one registry snapshot, and queued/running submissions together. It does not run task code, call migrations, write state, or emit reports. Task states include `running`, `pending` (with `Migrates` where applicable), `waiting`, `sleeping` (with `Until`), `completing`, and `blocked` (with reason/error).

At a phase boundary, a task hands over to a changed definition if it can reserve the record; otherwise, the old definition continues and receives `task_outdated` diagnostics. Each phase uses one `TaskRuntime.Registry()` snapshot. `TaskRuntime.Outcomes(ctx, ids)` reads terminal receipts in caller-specified order and rejects live tasks.

### Abort and reports

`Harness.AbortTask(ctx, id)` returns `AbortMarked` (`"marked"`) or `AbortTerminal` (`"terminal"`); unknown IDs return `ErrNotFound`. It durably marks before enabling scheduling, joins only the active run captured by that request (not a newly started abort handler), and stops joining on caller cancellation or Session admission sealing, not public `Done()`. Cancelling the wait does not undo the mark. Optional `TaskDefinition.Abort == nil` settles as `aborted`, unlike upstream's required abort handler. Do not synchronously abort a task from its own handler or abort a conversation scope containing it; that join waits for the handler to return. `Conversation.Abort` also waits for its selected work to settle.

`HarnessOptions.OnReport` supports `storage_failed`, `task_faulted`, `migration_failed`, `task_outdated`, `task_error`, `task_interrupted`, `extension_error`, `host_error` (with `Report.Callback`), and `listener_error`. Task reports carry copied task metadata and identify the relevant installing extension where applicable (empty for built-ins). A per-Harness FIFO worker invokes the callback serially and asynchronously; FIFO is enqueue order, not a global order among concurrent producers. Reports are best-effort diagnostics, not durable events. Callback panics are recovered and dropped; the worker continues with later reports. A blocked callback delays later reports but not scheduling or backend closure; accepted reports drain asynchronously, are not joined by `Done()`/`WaitClosed()`, and a callback may outlive shutdown. `TaskRuntime.Report` is nonblocking and does not assert that writes in its commit callback were committed. `AfterResponse`, `AfterTool`, `AfterTools`, `OnYield`, and tool hooks still record Go's `app.hook-error` entries instead of reporting `extension_error`; wrapper and structured-output reports wait for the tool suite.

### Persistence and scheduler errors

State v2 adds outcome and submission diagnostic fields. State v1 can be loaded and upgraded in memory; `Harness.Open` persists v2 in its reconciliation commit. Older binaries cannot safely reopen a v2 store, and future state versions are rejected. Direct `NewSession` users persist v2 on their next commit. This is a Go storage migration, not upstream file-format compatibility.

Storage failures are final, as upstream's are: the first error a storage commit returns, a certified `RejectedError` or a wrapped cancellation included, fails and seals the Session ([plan 0007](docs/plans/0007-upstream-commit-pipeline.md)). Cancellation is checked when a commit's job starts; once its callback ran, the commit is stored whatever happens to its caller's context. Scheduler bookkeeping callbacks that fail also fail the Session. `SessionEnd.Reason` is now `SessionEnd.Kind`.

### Restart accounting and clean close

`TaskRecord.Restarts` is an optional scheduler-owned count. Open increments it only for surviving `running` tasks (including abort invocations) and rewrites those tasks to `pending`. Other statuses and backoff deadlines are unchanged. Changed task state, new/upgraded abort marks, and held or terminal outcomes clear the count; structurally identical checkpoints, documents, memos, reservation, migration, and handover do not.

A clean close joins local invocations, then writes stopped tasks still `running` back to `pending` on the Session line without counting them. The write follows admitted commits, preserves their marks/checkpoints/memos/counts, runs no user callbacks, and publishes nothing. A failed Session writes nothing. Any close write-back error fails the Session and queues `storage_failed`; as upstream, `Close` returns only the backend close error, while `WaitClosed` exposes the first failure. An uncertain write can have applied: only reopening establishes the durable record.

Accounting leaves State version 2 unchanged. The first open counts `running` records even when an older build's clean close left them that way. Older State-v2 binaries can open the store, but their snapshot writes drop `restarts`.

`Settings.RestartLimit` follows upstream's number semantics as a `float64`: values below 1 and NaN select the default of 5, fractions round down, and `math.Inf(1)` never ends a task. At reservation, before definition resolution, a task whose count reached the limit ends `faulted` with `ErrorDetail` `{"reason":"restart_limit"}` and upstream's message when it would run an abort handler or a non-built-in kind; the fault holds while owned work cleans up and is reported as `task_faulted` with reason `restart_limit` once written. A generation whose abort handler was cut off ends its run `aborted`, with the fault message as `Detail` and its partial unconverted. Tasks committing a `failed` outcome whose `ErrorDetail` reason is `restart_limit` or `interrupted` produce `task_interrupted` with the pre-commit count in `Report.Restarts`. Built-in generation, tool, and compaction tasks end themselves at the limit when a phase starts, with upstream's messages, `restart_limit` details, and the salvage rule (a generation converts its partial at the limit and drops it past the limit); a tool's limit result uses Go's result form (message, then committed output) without upstream's structured diagnostics or `afterTool` hooks. Tool output and details live only in the `pi.live` slot (`pi.tool` 2), so they never reset the count; a safe rerun clears them first, and version-1 checkpoint output remains readable. A generation request that a crash cut off (its `request` phase runs with a nonzero count, after the limit check) is charged as a failed attempt without classification: its partial becomes an aborted entry, and it backs off under the retry policy or ends `interrupted` with upstream's text. A clean close still resends, and a charge that itself keeps crashing is ended by the restart limit.

### Retry policy and model-error classification

`DefaultRetrySettings`, `DefaultCompactionSettings`, `DefaultProgressSettings`, and `DefaultRestartLimit` are upstream's exported defaults. `Settings.Retry` ports `settings.retry`: pointer fields merge over the default (enabled, 3 retries, 2,000 ms doubling base delay, 60,000 ms cap) with JavaScript number semantics, and `retryDelayMs` keeps pi-ai's safe-integer replacement and cap. A generation retries only a transient error that is not a context overflow while `attempt <= MaxRetries`, keeping the failed attempt's partial as an aborted entry, backing off in a `retry` phase, and preparing the request again afterwards; a retry phase run before its deadline backs off again. `IsRetryableModelError` and `IsContextOverflowError` port pi-ai v1.5.2's pattern lists verbatim, with RE2 rewrites of two lookaround patterns and JavaScript's `\s` class; error types can answer through `Retryable()` and `ContextOverflow()`. `model.OpenAI` classifies the status and error text pi-ai would report before sanitizing it, and `model.Pi` returns the installed pi-ai's own classification. Compaction summaries retry under the same policy without the overflow check, resending their pinned request from a `retry` phase. Go numbers its own built-in versions: `pi.generation` 2 migrates version-1 records (`attempt = retry + 1`) and `pi.compaction` 2 accepts version-1 records unchanged (a missing attempt reads as 1). Backoffs sleep. `RetryMax` and `RetryDelay` are removed.

### Responses, tool results, and progress

How these areas behave in Go, with the differences that remain:

- `AfterResponse` sees every response, as upstream's `classify` does: a failed attempt reaches it with `StopReason: "error"` and `ErrorMessage`, and is stored as the error entry the hooks leave, which context derivation excludes. A rewritten message decides retries and overflow compaction by pi-ai's message patterns, as upstream classifies the message the hooks return; an unchanged one keeps the adapter's classification.
- A generation's phases are `prepare`, `request`, `retry`, `poll`, `tools`, `finish`, and `drain`. With `Settings.Stream.Deferred`, a capable provider answers with a `DeferredHandle` (`StopReason: "deferred"`); the generation sleeps until its poll (`pollAfterMs`, default 5000, shown in `pi.live.generation.deferred`), fetches it with `DeferredModel.FetchDeferred`, polls again while it is not ready, charges a poll a crash cut off as a failed attempt that polls again after its backoff, and cancels the provider's job when an abort, a cut-off, or an interrupted poll without a retry ends the run.
- Tool diagnostics are a flat list on `ToolResult` rendered in upstream's `<harness>` block. Results are bounded by `ToolDefinition.OutputLimits` (default 50 KiB and 2000 lines, head or tail) with a `truncated` warning; running output keeps its trailing 50 KiB and counts what it dropped (`DroppedBytes`, `DroppedLines`, reported as a `truncated` warning on results built from the slot), and its commits are throttled to `Settings.Progress.OutputIntervalMs` (default 100 ms), flushed when the call settles.
- Model context windows come from an optional `ContextWindowModel`: `model.Pi` reads Pi's catalog through the bridge, while `model.OpenAI` reports its `Window` field.
- Partials carry text, thinking, and tool calls whose arguments are parsed as they stream (`EventModel`, pi-ai's `parseStreamingJson` rules); each partial commit writes the whole partial message rather than upstream's appended changes. Deferred commits follow upstream's held documents: a held document is stored with the next commit that reads or writes it (transactions track their document reads), at its deadline, or at close; a window of 0 stores at once. Deadlines and context expiry run on the host's clock and timer (`HarnessOptions.Now`, `HarnessOptions.SetTimer`), as upstream's do. As upstream's, a generation's attempt marker, a tool slot's running status, and a nested slot's final arguments are progress commits too.

## Deliberate differences and remaining work

### Storage, transactions, and observation

Go commits copy on write and store each commit's changes ([plan 0006](docs/plans/0006-incremental-commits-and-record-storage.md)): SQLite keeps a row per record and converts a database of earlier versions (one whole-State row) inside its first write, and JSONL appends change lines. The Session holds the whole State in memory; internal reads, waits, and derived watches (`Conversation.Watch`, `View`, `WatchDocument`, `WatchWindow`, `WatchTaskGraph`, `Inspect`) share it and copy only what they return, while `Snapshot` and `Session.Watch` still copy it whole. Upstream uses indexed records and Chord document bases/deltas; neither Go JSONL nor SQLite files are compatible with upstream. One owning Session per storage is required; database transactions do not coordinate multiple schedulers. Storages read records one at a time through the optional `RecordStorage` (upstream's record-level `Storage` reads): memory and JSONL storage serve them from their copies, SQLite from indexed record rows. Over one, the Session's memory is bounded by work in use, as upstream's caches bound it ([plan 0008](docs/plans/0008-bounded-session-memory.md)): live tasks and open submissions, the context ranges of conversations used within `Settings.ContextRetentionMs`, documents used within `Settings.DocumentRetentionMs` or observed, and the conversation records in use, with caches for the rest; JSONL storage still holds its own whole copy, as upstream's does. Rewindable documents keep their revisions as records of their own (State version 4), so a write stores one revision, a retired document stays readable as of earlier entries, and an asOf fork copies the documents alive at its entry, retired since or not. Commits follow upstream's group commit ([plan 0007](docs/plans/0007-upstream-commit-pipeline.md)): a callback runs on the newest admitted state, a commit with writes joins the writer's batch while the line goes on, the writer stores every commit admitted while no store is in flight in one call (`BatchDeltaStorage`: one SQLite transaction, one JSONL sync), and publishes them in line order, each with its own sequence; a commit without writes never reaches storage. Performance equivalence and multi-writer coordination are not implemented.

A Go transaction callback cannot access its `Tx` after return, and committed values are detached, but Go cannot revoke a pointer already returned like a JavaScript proxy. Upstream table read-after-write restrictions are not reproduced. Go watchers coalesce to the latest full snapshot instead of preserving Chord frames. `Conversation.ScanEntries` pages raw history by entry ID range and order, and `Harness.TaskGraph`/`WatchTaskGraph` show every live task with its owner, state, phase, wait, sleep, held outcome, blocked reason, and owned conversations. `Conversation.WatchWindow` watches a windowed `ConversationView` (min/max splice, `From` resume, `Before`, built-in documents), and `ConversationTranscript` (`Conversation.Transcript`) merges its values into a client transcript with gaps, `LoadEarlier`, `FillGap`, and `Resume`; concurrent loads are serialized rather than shared. There is no Chord operation stream, typed watch-end result, synchronous observer, RPC/service/facet layer, coding-agent event compatibility layer, or offline multi-writer protocol. Go exposes `Done()`/`WaitClosed(ctx)` rather than an upstream `closed` promise.

The root conversation takes the reserved ID 1 (`RootConversationID`, upstream's `ROOT_CONVERSATION_ID`), and new stores mint other IDs from 2; a store from before the reservation keeps its root, and one created there takes ID 1 only if no record uses it. A conversation's provider session identity is on its record (`ConversationRecord.ProviderSessionID`, fresh for every conversation and fork) rather than in upstream's `pi.provider` document (`ProviderDoc`); hosts read it from the record. Task graph blocked reasons have constants (`BlockedMissingTask`, `BlockedTaskTooOld`, `BlockedMigrationFailed`).

### Agent execution, tools, and compaction

`model.OpenAI` supports text, images, and tools over OpenAI-compatible Chat Completions, sending user images in place (`ImageOffsets`), tool-result images after the tool messages, and pi-ai's placeholders with `NoImages` (one per run of images, in place), as pi-ai's openai-completions does. Go stores a message's text and images separately and places images by byte offset, so consecutive text blocks without an image between them are one text. The optional `model.Pi` adapter delegates authentication/provider transport to an installed SDK, but is not a native Go pi-ai port and is not guaranteed for every SDK/provider version. The bridge starts one Node process per request, does not load Pi AgentSession/project resources/extensions or refresh remote catalogs, and loses process-local caches. Messages carry images (`Message.Images`, `SubmissionRequest.Images`, `ToolResult.Images`) after their text, not interleaved with it; the bridge sends them as pi-ai image blocks and reads image input from the catalog (`ImageInputModel`), and estimates count 4,800 characters per image. The read tool returns PNG, JPEG, GIF, and WebP images within upstream's default limits without an image processor; with `tools.CodingWith(CodingOptions{Images: tools.StdImages()})`, a port of upstream's Photon processor on the Go standard library and `golang.org/x/image`, it also turns images upright by EXIF orientation, scales them into the limits, converts BMP, and re-encodes as PNG or JPEG at falling qualities, saying what it did. Limits are the model's catalog limits where `ImageLimitsModel` knows them (`model.Pi` reads pi-ai's `inputLimits.images.resize`), else upstream's defaults. Programs that call tools get upstream's structured output: `read` gives the shown text or the image, `bash` and `powershell` give `{output, truncated, fullOutputPath?, exitCode}`, and a tool without a schema gives its text, its one image, or its content list. `Submission.Abort` returns upstream's `aborted`, `already_placed`, or `settled`; `Conversation.ContextView` and `TaskRuntime.Context` read the model context view (head marker, entries, contributions, messages), optionally as of an entry. Task and tool runtimes port upstream's helpers: `TaskRuntime.Agent` (the resolved agent: offered, callable, and deferred tools and sections), `Task`, `WaitTask` (an in-memory wait), `Conversation`, and `Entry`, and `ToolRuntime.Diagnostic` (stored in the call's slot with its throttled output and placed before the result's own diagnostics, also on results built from the slot) and `RetainedOutput`. Nested slots carry dropped counters and diagnostics too. `Settings.Extensions` ports `settings.extensions`, the selection of an agent that names none, which `Agent.ExtensionEdits` edits (upstream `extensions: {add, remove}`); `Agent.RemoveTools` ports `tools: {remove}`, and loading a tool takes it out of the removed ones. `Settings.Stream` ports `settings.stream` (transport, timeouts, thinking budgets, provider retries, headers, metadata, cache retention) onto every model request as it is sent; the bridge passes it to pi-ai, keeping SSE and no provider retries when unset, and `model.OpenAI` honors its headers and timeout. The Go boundary does not expose image generation or classifier APIs, virtual models, or deferred model handles (`stream.deferred`). See [model/README.md](model/README.md).

Harness-written tool results follow upstream: an error diagnostic with a code (`tool_unavailable`, `invalid_arguments`, `blocked`, `interrupted`, `restart_limit`, `aborted`, `abandoned`) rendered in a `<harness>` block after the content, built from the slot's output for interruptions and aborts, and passed through `AfterTool` hooks as every result is (except past the restart limit and in an abort handler's last attempt). Hook failures are reported as `extension_error`. Sequential rounds (`Settings.ToolExecution` or a tool's `ExecutionMode: "sequential"`) start one call at a time in call order, and a call to a tool its request did not offer gets a task that settles `tool_unavailable` without resolving the name; an aborted round gives unstarted calls `aborted` results. Nested calls (`ToolRuntime.ExecuteTool`) run as owned `pi.tool` tasks tagged `nested`, keyed so a rerun finds calls already made, with results stored for the caller and slots in `pi.live.nestedTools`; calls left running are aborted when the caller settles, and a non-replay-safe caller's calls are abandoned on restart. `ToolDefinition.Callers` restricts who may call a tool, and `StructuredOutputSchema` validates the structured output programs receive. `Agent.ModelTools` selects the offered tools (an exact list, or every model-callable tool minus `Remove` plus loaded deferred tools in `Add`), `ToolDefinition.Deferred` tools wait to be loaded, and a result's `AddTools` loads tools from the next request on. `tools.ToolSearch()` ports the `tool_search` extension with upstream's BM25 ranking (CJK, Thai, and kana split per character instead of `Intl.Segmenter` words). Code mode is not implemented: it needs a JavaScript sandbox. Tool-round context ordering and missing-result synthesis are implemented, with upstream's `missing_result` details.

Compaction follows upstream's algorithm (`select`, `summarize`, `retry`): `KeepRecentTokens` decide the kept range at run time with upstream's cut rules and 3.5-characters-per-token estimates, the summarized messages are serialized as a transcript with upstream's prompt, and the summary is placed with upstream's prefix. Blocking and background threshold compaction in generation preparation, overflow compaction after a context-overflow error, `Settings.Compaction` and per-conversation `Agent.Compaction` with model overrides, `Hooks.BeforeCompact` (decline or supply a summary), and `pi.live` compaction status are implemented. Compaction requests do not pass through generation hooks; summaries and resets do not delete original entries. Local environments provide filesystem/shell access, not a VM or container boundary; `tools.PowerShell()` runs PowerShell programs directly (pwsh, then powershell) through `ArgvExecutor`; the Cloudflare Durable Object adapter, remote environment protocol, bounded binary/directory readers, and filesystem watcher are absent. The bash tool follows upstream: bash when installed (else `/bin/sh`), an optional `timeout`, the last 2000 lines or 50 KiB with a `truncated` warning, the full output spilled to a temporary file (`full_output`), and a nonzero exit as an error result with an `exit_code` diagnostic; JSONL currently needs Unix advisory locks. The edit tool follows upstream's matching: a byte-order mark and CRLF endings are kept, an inexact match falls back to fuzzy matching (NFKC, trailing whitespace, smart quotes, dashes, special spaces) that rewrites only the lines it touches, and errors use upstream wording; details carry upstream's numbered `diff`, a unified `patch`, and `firstChangedLine` from a Go Myers line diff, whose choices in ambiguous alignments may differ from jsdiff. The read tool streams text through `FileOpener` (implemented by `LocalEnv`) and follows upstream's selection, head truncation, and continuation diagnostics; it reads no images. Atomic replacement does not preserve hard-link aliases.

Streamed partial answers are committed to `pi.live.generation.message` at most every `Settings.Progress.PartialIntervalMs` (default 100 ms), with one commit in flight, as upstream does. Tool output is throttled the same way (`OutputIntervalMs`). Both are deferred commits (`CommitOptions{Deferred}`, upstream `PROGRESS_COMMIT`): shown at once and stored with the next commit that reads or writes them, within `Settings.Progress.PersistWithinMs` (default 1,000 ms), or at close; a crash loses what was not stored yet. `Harness.CommitWith` and `TaskRuntime.CommitWith` take the same options; a deferred commit that changes anything but existing conversation documents with latest history and the initial fork is stored like an immediate one. Prompts and tools follow spec §7.4: generation renders the agent's sections, replays the transcript's `pi.system` system messages (`Message.Sections`, `ToolsAdded`, `ToolsRemoved`), and appends the minimal patch, a remove-all/re-add-all pair for an order change, or, after a head marker, a complete baseline whose `ContextEdit` omissions drop retained earlier ones; context derivation ports upstream's edits and leading baseline. The Pi bridge sends system messages in place for pi-ai to keep or fold per provider; `model.OpenAI` folds them (`CollapseSystemMessages`). `pi.system` entries written by earlier versions held only a journal and contribute nothing. Sections render as upstream's, from a `PromptInput` (conversation, resolved agent with the offered tools, the preparation's environment, the sections shown, and document reads): wrapped as `<name>` unless `Untagged` (upstream `tag: false`), an empty render is an empty section, `ErrOmitSection` omits one (upstream `undefined`), and `Agent.Instructions` (`*string`) adds the `instructions` section whenever it is set, even empty. Tool declarations carry `ConstrainedSampling`, and estimates count UTF-16 code units like pi-ai. The Pi adapter forwards session IDs for best-effort provider affinity without retaining process-local continuation caches. Usage and cost are best-effort; interrupted streams without usage receipts cannot provide exact billing totals. Custom models/tools must honor cancellation. No distributed scheduler/lease/fencing implementation is provided.

### Release status

Experimental. APIs and storage migrations can change. Do not infer Go API stability from upstream version numbers. No production readiness, benchmark equivalence, exhaustive crash/power-loss proof, or upstream conformance is claimed. Tests use fake models, local HTTP servers, and local storage; they are an independent Go suite.
